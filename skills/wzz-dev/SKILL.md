# WZZ 软件开发 SOP

从用户要求的阶段开始，先确定本轮目标、已有输入和交付终点。SDD 在这里指规格驱动开发。让验收条件（AC）连接规格、设计、任务、实现、测试和候选版本。

## 接手项目

- 先读仓库说明、已有需求、相关代码入口、测试命令与近期改动。确认当前基线、已有能力和历史失败。新项目先定位目标用户、首个可演示流程与运行约束。
- 按请求裁剪流程。小缺陷用一张卡记录复现、预期、修复和回归；普通功能维护规格、设计和任务；跨系统或数据迁移再补兼容设计、迁移演练和恢复方案。沿用项目现有文档和目录。
- 区分业务决定、可逆的工程假设和实测事实。对会改变用户结果且无法从现有材料确定的取舍，请业务负责人裁决；独立工作继续推进。用户只要求方案、拆工或评审时，交付该阶段成果即可。

## 八个阶段

| 阶段 | 输入 | 产物与完成判断 |
| --- | --- | --- |
| 1 立项与范围 | 用户痛点、现有做法、时间与资源 | 一页 PRD 或简报，写明目标用户、真实场景、首版边界、暂缓项、成功指标及衡量方式。由业务负责人决定优先级。 |
| 2 需求规格 | 已定目标、用户流程、业务规则 | 在 spec.md 或现有需求载体记录带编号的 AC。每条写前置条件、触发动作、可观察结果；覆盖会改变判断的异常、权限与边界。质量指标注明环境和衡量口径。 |
| 3 技术设计 | 规格、既有架构、数据和运行约束 | 在 design.md 或现有设计记录技术栈及取舍、模块与数据流、接口契约、表与约束、失败处理和测试策略。把每条关键规则映射到负责组件和验证方法。需要 DDD 时，与业务方统一术语、边界、状态及不变量。 |
| 4 计划与拆工 | AC、技术设计、共享契约 | 在 tasks.md 或看板记录有依赖关系的任务卡。每条必需 AC 都有实现与验证责任人，每张可开工的卡都给出输入、可写范围和交付证据。 |
| 5 开发与自测 | 任务卡、基线、工作环境 | 交付改动、测试、必要的迁移与配置、版本标识、自测命令和实际结果。适合 TDD 的规则或缺陷，先验证用例因预期原因失败，再实现、重构、复跑。 |
| 6 集成与系统测试 | 各任务交付、测试环境、原始 AC | 生成集成候选版本。主 Agent 核对真实差异和测试断言，运行适用的构建、契约、集成、回归和端到端测试，逐条 AC 附证据及结论。 |
| 7 业务验收与发布 | 经验证的候选制品、真实场景、发布条件 | 准备 UAT 步骤与样例数据，由业务方实际验收并记录结论。对已授权的发布，使用同一已验收制品，记录配置、迁移顺序、冒烟结果、观察窗口、停止条件和恢复负责人。 |
| 8 运维与迭代 | 线上版本、监控、用户反馈、产品指标 | 对比目标与实际效果。故障先恢复并验证数据；随后补复现、回归、告警及操作手册。将业务变化回写规格，列出受影响任务和下一轮优先级。 |

## 派工与变更

先切出一条能演示的用户流程。共享接口先约定请求、响应、错误、字段语义及样例；数据库设计明确约束与写入责任。契约稳定、工作区独立且结果可分别验证时，可按当前工具与授权分派子 Agent；单 Agent 也可顺序执行相同任务卡。

主 Agent 持有任务依赖和验收表。实现者负责约定模块及自测；独立测试者根据原始规格推导用例。共享类型、迁移序列等指定一个写入负责人。契约变化时，更新版本，列出提供方、消费方和受影响用例，重开相关任务。任务没有代码依赖却会同时修改同一文件时，串行处理或先明确所有权。

## 验收与交接

- 在同一候选版本上检查关键用户路径及其副作用。分别通过的分支、模拟接口结果和页面截图可作辅助证据。缺少集成运行记录时，工程验收记为“未验证”，列出补验命令或场景及负责人。
- 证据按 AC 记录候选版本、环境、测试入口、预期、实际、日志和状态。实现有误时退回任务卡并复测；预期有歧义时回到规格。发给业务方的 UAT 交接写清目标版本、数据准备、操作和用户可见结果。
- 结项时报告真实完成范围、证据位置、遗留风险和下一责任人。业务验收、生产发布、线上观察各自使用其实际记录；执行范围按用户授权确定。

编写规格、技术设计、任务卡或验收记录时，按需取用[开发模板与预约示例](references/delivery.md)中的相应部分。
